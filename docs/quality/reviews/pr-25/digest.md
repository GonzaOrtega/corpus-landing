# PR #25 · Redact secrets from logs and events, retry failed Sentry init

## Like you are five
corpus-landing is the public early-access page for Corpus, an Android-first language-learning product. Anyone can visit it, read what the product is, and leave an email address to be told when it launches. They confirm that address by clicking a link in a mail, and they can later use a second opaque link to change their mind and leave. There are no accounts and no passwords: the links themselves are the only key. One day the site sends a single launch mail to everyone who stayed, and then it turns into a plain 'Get Corpus' page. It is built with Next.js on Vercel, keeps its list in a Postgres database at Neon, and sends its mail through Resend. The code is arranged so the rules of the product sit in the middle and never reach out to any outside service directly; the parts that talk to the database, the mail provider and the error tracker are plugged in around the edge. The repository is public, so its history and its documents are part of what it ships.

An earlier change gave the running site a way to tell its operators when something breaks, by sending error reports to a service called Sentry. The review of that change ended with thirty-one smaller problems written down but left unfixed. This change closes twenty-nine of them; two turned out to need no work. Most of the fixes are about what must never leave the machine. Reports are now cleaned in more places and more thoroughly: browser timing reports, the extra fields attached to log lines, anything buried too deep to inspect, database addresses including the host name, and the question-mark and hash parts of every web address that shows up in a report or a stack trace. The cleaning was also made fast, because one of the old text rules took whole seconds on a long line, and made careful enough not to mangle innocent text such as a colour code or a button name. The rest of the fixes make failures visible instead of silent: a failed start-up now tries once more thirty seconds later, a reporting failure can no longer break the visitor's request, the stand-in reporter writes one line to the log instead of throwing everything away, and a local test run no longer forwards real browser reports to the live service. There are also new tests for the two error pages, for the forwarding route, and for the list of values that must never be logged, and the coverage thresholds were raised to match what is now actually measured.

Four helpers read this change on their own and wrote down twenty-one things. Fifteen are small, and the gate set those aside by itself. Six are big enough that you have to decide about them.

The most serious one is about hiding email addresses. When something goes wrong, the site writes a note about it and sends that note away to be read by its operators. Before sending, it blanks out anything private. Somebody was making that blanking-out faster and, while doing it, told the email rule to look at only the first sixty-four letters of an address. An address longer than that is now only half hidden: the beginning of it goes out readable. The sign-up form lets people use addresses that long, so this is a real person's address, not an imaginary one. The helper proved it by running the real code, and then checked whether the limit was even needed for speed. It was not. That rule was never the slow one.

Two are about the little door the site uses to pass browser reports along. If a visitor's browser starts sending a report and then goes away half-way through, the door falls over and nothing is written down about it, even though the door's own note promises that every failure is recorded. The other one: while the site is being tested, the door is told to throw everything away, but it is told in a way that looks exactly like "nobody ever set this up". If that ever happened by accident on the real site, every browser report would quietly disappear and nothing would say so.

One is about signing up. A new shared wrapper was added so that a failure in the monitoring code can never break a visitor's request. It works, but it is a little too eager: if the monitoring part trips after the sign-up has already gone through, the wrapper throws the good result away and tells the visitor it did not work. They sign up again and get a second confirmation mail for a place they already have.

The last two are missing checks rather than broken behaviour. Nothing proves that the stand-in reporter — the one used when no tracker is set up — was actually handed a working notebook to write in; it quietly ignores a broken one, so the whole point of the fix could stop working with every test still green. And the filter for extra bits attached to log lines only switches on when it sees one exact word copied from an outside library. Nothing anywhere pins that word down, so an update to that library could rename it and switch the filter off without a single test noticing.

What you need to decide: for each of the six, whether it gets fixed in this pull request or written down for later. If you want them all done, saying so is enough.

- **R-08 · later** · noop-error-reporter.adapter.ts · The stand-in reporter's whole purpose is to write one line instead of discarding the failure, but if that write fails it discards the failure anyway with an empty catch and no fallback. · Below the severity floor (important)
- **R-09 · later** · observability.ts · The comment says a boundary is never handed a reporter the reporting service will quietly drop, but the rule it uses only checks that an address was supplied, not that it is usable — so a typo leaves failures vanishing at runtime with no log line either. · Below the severity floor (important)
- **R-10 · later** · instrumentation-client.ts · When browser reporting fails to start twice in a row, the only record is a line in that one visitor's own browser console, which no operator ever sees — so 'reporting was off for some visitors' stays invisible. · Below the severity floor (important)
- **R-11 · later** · never-log-fixture.test.ts · A new test checks that the list of values-never-to-log has no duplicates, but the list is built by de-duplicating, so that check can never fail and proves nothing. · Below the severity floor (important)
- **R-12 · fix** · observability.ts · Nothing checks that the stand-in reporter is actually given a working log writer, and the reporter quietly ignores a broken one, so the new "write one line instead of throwing it away" behaviour could stop working without any test noticing. · In scope, in the threat model, important
- **R-13 · fix** · sentry-options.ts · The stricter filter for log-line extras only switches on when a report carries one exact marker string copied from the reporting library, and no test pins that string or covers what happens when it does not match. · In scope, in the threat model, important
- **R-14 · later** · sentry-options.test.ts · A test named for proving that missing fields stay missing cannot actually detect an invented field, because the comparison it uses treats a present-but-empty field as absent. · Below the severity floor (important)
- **R-15 · later** · error.test.tsx · The new error-page tests replace the framework's after-render hook with one that ignores its dependency list, so a change that stops a second, different failure from being reported would still pass. · Below the severity floor (important)
- **R-16 · later** · next.config.ts · The new build-time warning about a misspelt reporting address is tested on its own but nothing checks that the build configuration still calls it, so deleting the call breaks nothing. · Below the severity floor (important)
- **R-17 · later** · instrumented-action.ts · The new shared wrapper turns every failure into the polite retry answer, including the framework's own internal signals, and only a comment records that today's actions never raise one. · Below the severity floor (important)
- **R-18 · fix** · sentry-options.ts · The rule that hides email addresses in error reports was given a length limit of 64 characters, so an unusually long address is only partly hidden — the beginning of it is sent to the error tracker in the clear. · In scope, in the threat model, important
- **R-19 · later** · never-log-fixture.ts · The shared list of values that must never leave the machine only contains short sample values, so nothing in the suite exercises the new length limits the scrubber now applies. · Below the severity floor (important)
- **R-20 · later** · monitoring-route.handler.ts · The new chunk-by-chunk body reader in the forwarding endpoint has no failure path, so a caller that starts sending and then drops the connection produces a server error with no log line, although this handler promises that every fault is recorded. · Below the severity floor (important)
- **R-21 · later** · observability.ts · Wherever error reporting is switched off, a fresh logger is now built from scratch every time a form submission or link lookup asks for a reporter. · Below the severity floor (important)
