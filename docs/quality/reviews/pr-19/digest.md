# PR #19 · Add Sentry observability: error reporting, tracing, and logs

## Like you are five
corpus-landing is the public early-access page for Corpus. Anyone can visit it, read what the product is, and hand over an email address to be told when it launches. They confirm that address by clicking a link in a mail, and they can later use a second opaque link to change their mind and leave. There are no accounts and no passwords: the links themselves are the only key. One day the site will send a single launch mail to everyone who stayed, and then it turns into a plain 'Get Corpus' page. It is built with Next.js on Vercel, keeps its list in a Postgres database at Neon, and sends its mail through Resend. The code is arranged so the rules of the product sit in the middle and never reach out to any outside service directly; the parts that talk to the database, the mail provider and now the error tracker are plugged in around the edge.

This change gives the running site a way to tell its operators when something breaks. Until now, when a signup failed, the page deliberately showed the visitor the same polite 'please retry' message no matter the cause, and the real reason was thrown away, so nobody could tell a database outage from a rejected spam check. The nightly cleanup job failed silently too. This adds Sentry: errors from the server, the browser and the cleanup job are now reported, slow operations are traced, and the log lines the site already writes are collected somewhere a human can read them. The hard part, and the part worth reviewing, is what must NOT be sent: email addresses, the secret links, the spam-check score, the mail provider's replies, the database address and every secret are stripped before anything leaves the machine, and the code tries to do that three separate times over in case one layer misses. It also has to stay quiet during tests and building, and it must not slow the page down enough to fail the site's speed budget.

The same four reviewers read the nine fixes. The good news first: the two things that actually mattered are genuinely fixed, and they checked properly rather than taking anyone's word.

The secret key can no longer get out. One reviewer built a fake crash report and hid the key in every pocket it could think of — the page address, the "where did you come from" field, the trail of what the visitor clicked, the error text itself, the timing records. It ran the real cleaning code over all of it. The key came back blanked out every single time. A second reviewer went at it from the other side, checking the key's own alphabet to make sure it could never contain a character that would let it slip through the net. It can't.

The "something went wrong" screen now reports properly, and — the thing I was most worried about — it does not drag the error tracker in early and slow the page down. Both reviewers confirmed the tracker is still only fetched once something has actually gone wrong.

The new private mailbox we built to replace the vendor's wide-open one also held up. Two reviewers tried to trick it into forwarding somewhere else using lookalike addresses and malformed input. It refused every time, because it never reads the destination from the request at all — it only ever uses its own.

Now the five things still open, and they are all of the same family: the fixes work, but not enough is watching them.

Nobody is told if the new mailbox breaks. If it starts turning messages away, every browser error report stops arriving, and that looks exactly like a quiet week with no problems. That is the one I would not ship without.

Anyone on the internet can post to that mailbox as often as they like, and each post costs us a little hosting money. It is much better than what it replaced, and the provider caps the damage at the far end, but nothing stops the flood at our door.

And three tests that look like they are guarding something but are not quite: one checks that the error tracker was switched on but never checks it was switched on with the privacy filters attached; one never proves the mailbox ignores a destination written inside the message itself; and one checks that the speed-test config still contains the right words rather than that it still does the right thing.

Two smaller notes I have to own up to: two comments in the code and the handbook now contradict each other about whether a local speed test can leak, and the handbook is the one that is right. I told you earlier that one fix had accidentally solved that problem. I was wrong, I checked, and it has not.

What you need to decide: this is the last round. Whatever you say fix gets fixed and the gate closes. Whatever you leave becomes a ticket instead of a blocker.

- **R-37 · later** · monitoring-route.handler.test.ts · A size-limit test is named for a request that understates how big it is, but the request it builds declares no size at all, so the case a reader would assume is pinned is not the case that runs. · Below the severity floor (important)
- **R-38 · later** · never-log-fixture.ts · The shared list of forbidden sample values is maintained by hand next to the object it is derived from, so adding a new forbidden field to the object without also adding it to the list would quietly shrink what both test suites check. · Below the severity floor (important)
- **R-39 · later** · e2e-runtime-config.test.ts · The pipeline marker that keeps a local Lighthouse run from behaving like a real deployment was added to the config but is asserted nowhere, so removing it would go unnoticed. · Below the severity floor (important)
- **R-40 · fix** · monitoring-route.handler.ts · Anyone on the internet can make the site forward messages to its error-tracking provider as many times as they like, at the site's expense, because the endpoint has no rate limit and the only 'password' it checks is a pair of numbers that is published in the site's own JavaScript. · In scope, in the threat model, important
- **R-41 · later** · sentry-options.ts · One of the four text-cleaning rules gets dramatically slower the longer a piece of text is, so an unusually long line inside an error report can freeze the request that is trying to send it. · Below the severity floor (important)
- **R-42 · later** · sentry-options.ts · The new rule that blanks out anything after a '#' is much broader than the comment admits: it also destroys the element identifiers in click history, framework error numbers and ordinary text, which is exactly the detail an engineer needs when reading a report. · Below the severity floor (important)
- **R-43 · later** · sentry-options.ts · A comment states that the page address field is the only place the subscriber's secret link can travel, which is not true — two other fields carry it as well, and those are protected only by the new text rule, not by the structural fix. · Below the severity floor (important)
- **R-44 · later** · sentry-options.test.ts · The tests prove the secret link is stripped from the page-address field, but never prove it is stripped from the two other fields that carry it, which are the ones relying on a pattern that a future edit could weaken. · Below the severity floor (important)
- **R-45 · later** · sentry-options.ts · The check that recognises the error-tracking address only accepts a two-letter region code, so a legitimate address with a longer region name would silently switch off all browser error reporting with no warning anywhere. · Below the severity floor (important)
- **R-46 · later** · monitoring-route.handler.ts · When a caller does not declare how big the upload is, the whole upload is pulled into memory before the size limit is applied, so the limit bounds what gets forwarded but not what gets held. · Below the severity floor (important)
