# PR #19 · Add Sentry observability: error reporting, tracing, and logs

## Like you are five
corpus-landing is the public early-access page for Corpus. Anyone can visit it, read what the product is, and hand over an email address to be told when it launches. They confirm that address by clicking a link in a mail, and they can later use a second opaque link to change their mind and leave. There are no accounts and no passwords: the links themselves are the only key. One day the site will send a single launch mail to everyone who stayed, and then it turns into a plain 'Get Corpus' page. It is built with Next.js on Vercel, keeps its list in a Postgres database at Neon, and sends its mail through Resend. The code is arranged so the rules of the product sit in the middle and never reach out to any outside service directly; the parts that talk to the database, the mail provider and now the error tracker are plugged in around the edge.

This change gives the running site a way to tell its operators when something breaks. Until now, when a signup failed, the page deliberately showed the visitor the same polite 'please retry' message no matter the cause, and the real reason was thrown away, so nobody could tell a database outage from a rejected spam check. The nightly cleanup job failed silently too. This adds Sentry: errors from the server, the browser and the cleanup job are now reported, slow operations are traced, and the log lines the site already writes are collected somewhere a human can read them. The hard part, and the part worth reviewing, is what must NOT be sent: email addresses, the secret links, the spam-check score, the mail provider's replies, the database address and every secret are stripped before anything leaves the machine, and the code tries to do that three separate times over in case one layer misses. It also has to stay quiet during tests and building, and it must not slow the page down enough to fail the site's speed budget.

Four reviewers read this change on their own, without seeing each other's notes. Between them they raised twenty-six things. Sixteen are small and have already been parked for later automatically. Ten are waiting on you.

The one that matters most: when someone wants to change or cancel their early-access signup, we email them a link with a secret key in it, and that key is the only thing standing between a stranger and that person's record — there are no passwords here, the link *is* the password. The key sits in the tail end of the web address, after the "#". This change starts sending crash reports to an outside company, and those reports include the full web address of the page the person was on, tail end included. The code written to wipe secrets out of those reports knows how to spot several shapes of secret, but not that one. So if the manage page breaks in someone's browser before it has had the half-second it needs to tidy the address, their key gets posted to a third party. Two reviewers found this separately. The privacy notice this very change adds to the site currently promises the opposite.

The second one: this change adds a "something went wrong" screen, and that screen asks the crash reporter to write the error down. But the crash reporter is deliberately started late, after the page has finished loading, so that it doesn't slow the site down. A crash during loading therefore happens while the reporter is still asleep, and the note goes nowhere. The screen exists to catch exactly those crashes. Two reviewers found this one too.

One thing I owe you straight: a third reviewer reported something serious-sounding — that the switches turning off data collection were misspelled and silently doing nothing. It was wrong. It had checked against an older version of the library than this project actually installs. I pulled the real version and read it myself: the switches are correct and they do work. That is R-06 in the list, and my recommendation is that you drop it rather than fix it. I have written the proof into the record so nobody re-raises it next round.

What you need to decide: for each of the ten, whether it gets fixed before this merges or pushed to later. You can accept the whole list, or name the ones you want changed. Nothing gets touched until you answer.

## In plain words
Round 1 looked at the whole change and found 26 things. I sorted them: 10 to fix now, 16 for later, 0 that do not apply, 0 waiting for you.

- **R-01 · fix** · sentry-options.ts · The web address of the page is forwarded to Sentry exactly as it is, and the part after the '#' is never hidden — but that is precisely where the subscriber's secret management key sits while they are on the manage page, so a browser error report from that page can carry the key out of the building. · In scope, in the threat model, critical
- **R-02 · fix** · error.tsx · The 'something went wrong' screen asks Sentry to record the error, but nothing has switched Sentry on at that moment, so the report is quietly dropped — losing exactly the browser errors these screens exist to report. · In scope, in the threat model, important
- **R-03 · later** · sentry-options.ts · Three cleaning steps are installed for errors, traces and log lines, but not for the standalone performance measurements the browser sends on their own, so if browser performance tracking is ever switched on those would leave uncleaned. · Below the severity floor (important)
- **R-04 · fix** · sentry-options.ts · The '/monitoring' address the browser reports through is an open, unauthenticated forwarder: anyone can post anything through the site's own domain to any Sentry account, at the site's expense. · In scope, in the threat model, important
- **R-05 · later** · maintenance-schedule.ts · A comment tells the next reader that a particular test guards the nightly job's schedule, but no test by that name exists — the real check lives somewhere else. · Below the severity floor (important)
- **R-06 · fix** · sentry-options.ts · The block meant to switch off everything the reporting library collects by itself uses two setting names the library does not recognise, and merely supplying the block makes the library start from "collect everything", so request headers and URL query parameters end up switched on rather than off. · In scope, in the threat model, important
- **R-07 · later** · instrumentation-client.ts · Browser error reporting is started from an idle moment with no deadline and is never retried, so in a background tab, or after a single failed download, the page reports nothing for the rest of its life and nothing says so. · Below the severity floor (important)
- **R-08 · later** · join-early-access.action.ts · The new tracing wrapper, and the request-header lookup it needs, sit outside the signup action's own safety net, so a failure inside the monitoring code now breaks the form instead of showing the visitor the polite "please try again" message. · Below the severity floor (important)
- **R-09 · later** · noop-error-reporter.adapter.ts · Wherever no reporting address is configured - every developer machine, and any preview not yet set up - the failure is handed to an empty function, so it still vanishes with no log line anywhere. · Below the severity floor (important)
- **R-10 · later** · sentry-options.ts · The design says fields picked up from the application log are re-checked against the short list of fields allowed to leave the machine; for log records they are only checked against a list of forbidden names, so any other field a logger attaches still goes out. · Below the severity floor (important)
- **R-11 · later** · observability.ts · Whether boundary failures get reported is decided when the site is built, while the reporting library itself decides when the site runs, so the two can disagree and failures can be dropped silently while everything else is reported normally. · Below the severity floor (important)
- **R-12 · fix** · sentry-options.ts · Every test of the privacy scrubbers calls them directly, and no test checks that they are actually attached to the settings handed to Sentry, so deleting one line would silently send everything unscrubbed while the whole suite stays green. · In scope, in the threat model, critical
- **R-13 · fix** · sentry-options.test.ts · The approved design says the Sentry tests must check against the same banned-values list the logger tests use, but the two lists are separate copies that have already drifted apart. · In scope, in the threat model, important
- **R-14 · fix** · sentry-options.ts · The text scrubber never touches the part of a web address after the '#', which is exactly where this product puts its secret management link, and no test covers that case even though one test looks like it does. · In scope, in the threat model, important
- **R-15 · fix** · resolve-management.action.ts · Nothing checks that the three form submissions are traced without their form contents and without their answer, so a one-word change could start attaching the visitor's masked address and state to the trace unnoticed. · In scope, in the threat model, important
- **R-16 · fix** · e2e-runtime-config.test.ts · The design and the runbook both promise that the three local measurement runs never report to Sentry, but the new test only checks two of them, and the third genuinely does not blank the setting. · In scope, in the threat model, important
- **R-17 · later** · error.tsx · The two screens that catch failures happening inside the visitor's browser, and the loader that starts the browser reporter after the page settles, have no tests at all. · Below the severity floor (important)
- **R-18 · later** · proxy.ts · The address the browser sends its reports to is written out by hand in two places, and unlike the cron schedule this PR does pin, nothing checks the two stay the same. · Below the severity floor (important)
- **R-19 · later** · maintenance-schedule.ts · A comment sends the next maintainer to a test file that does not exist; the real check lives somewhere else. · Below the severity floor (important)
- **R-20 · later** · sentry-options.ts · The scrubber stops cleaning once a payload nests more than twelve levels deep and hands the rest through untouched, and no test pins that boundary. · Below the severity floor (important)
- **R-21 · later** · management.actions.test.ts · A check meant to prove the secret link never reaches the reporter is written so that it can never fail, which makes the coverage look stronger than it is. · Below the severity floor (important)
- **R-22 · later** · unsubscribe.action.ts · The signup form has a test proving that a broken configuration is still reported before the visitor sees the polite retry message; the two management actions have the same code path with no such test. · Below the severity floor (important)
- **R-23 · fix** · e2e-runtime-config.test.ts · The promise that the speed-measurement run never reports anything is not actually implemented, so a developer with real credentials in their local settings file will silently send local traffic to the live error tracker. · In scope, in the threat model, important
- **R-24 · later** · sentry-options.ts · The rule that blanks out credential-carrying web-address parameters only fires when the parameter is preceded by '?' or '&', which is never true for the very field the scrubber goes out of its way to keep. · Below the severity floor (important)
- **R-25 · later** · sentry-options.ts · The claim that the database address is stripped before anything leaves the machine is stronger than what the code does: only the username and password are removed, and the database host still travels on every outgoing-call trace. · Below the severity floor (important)
- **R-26 · later** · sentry-options.test.ts · No test feeds the scrubber an event shaped like one from a real browser on the management page, so the case where the secret link sits in the address is never checked. · Below the severity floor (important)
